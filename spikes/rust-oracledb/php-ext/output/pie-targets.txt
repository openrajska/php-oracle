Build environments
  Linux:   php:8.4-{cli,zts}-{bookworm,alpine} on ubuntu-24.04 / ubuntu-24.04-arm (native, no cross).
           bookworm: build-essential libclang-dev. alpine: build-base clang clang-libclang.
  macOS:   macos-15 + shivammathur/setup-php (phpts nts|zts). Xcode's libclang is found; no brew llvm.
  Windows: windows-2025 + shivammathur/setup-php (vs17 builds). Runner LLVM; aws-lc built with no
           extra NASM/CMake setup; ext-php-rs downloads the PHP devel pack itself. linker = rust-lld.
  PHP 8.4.28 everywhere. Linker flags: .cargo/config.toml (dynamic_lookup on macOS, -crt-static on musl).

Fixes found by the first run
  1. Alpine: clang-libclang alone lacks clang's builtin headers (mmintrin.h on x86_64, arm_neon.h on
     arm64) that PHP's zend_types.h includes; bindgen fails. Install `clang` too.
  2. Windows: RUSTC_BOOTSTRAP=1 or nightly is not enough. The extension crate itself must declare
     #![cfg_attr(windows, feature(abi_vectorcall))], because #[php_function] expands to
     extern "vectorcall" in our crate (E0658). Stable 1.100 + RUSTC_BOOTSTRAP=1 then works like nightly.

Notes
  - The glibc floor is 2.34 even when built on bookworm (2.36): RHEL 9 / Ubuntu 22.04 and newer load it;
    RHEL 8 (2.28) and Debian 11 (2.31) would need a pinned older target (not tried). The build image
    sets the floor: the same crate built in the ddev web container (Debian 13) needs GLIBC_2.38.
  - Linux artifacts depend only on libc and libgcc_s; macOS only on libSystem. No Instant Client,
    no OpenSSL: TLS is statically linked aws-lc.
  - Not tried: macOS x86_64 (out of v1 per the PIE research), PIE itself installing the assets
    (asset naming/packaging belongs to the release pipeline, not this question).
